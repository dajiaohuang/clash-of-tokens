# 按使用场景优化性能

2026-09-09，本轮检查覆盖频繁模型发现、长对话、图片输入、小型分块上传排队、大请求、突发多账号调度、慢客户端和管理状态更新。

## 已修改与测量

Windows amd64、i9-14900KF、Go 1.27.1；微基准各三次、每次 300 ms，表中为中位数。

| 场景 | 修改前 | 修改后 |
|---|---:|---:|
| 100 账号、每账号 10 模型的模型列表响应 | 521.777 µs；586,930 B；8,045 次分配 | 166.919 µs；163,317 B；1,014 次分配 |
| 100 条讨论 image 的纯文本消息检查 | 23.921 µs；3,257 B；201 次分配 | 8.781 µs；48 B；1 次分配 |

模型列表用带类型的结构体替代逐模型 map，并按本次启用状态预留切片容量。每次请求仍读取当前状态，启用/停用立即反映，不引入缓存过期问题。

图片能力检测不再因为文本中出现 image 就逐字段调用 JSON 解码器。常见标记直接匹配，Unicode 转义继续解码；同时修复了完全转义的图片标记可能漏检的问题。普通换行和引号转义无需单独触发完整图片扫描。完整 JSON 合法性校验仍保留。

## 小请求排在长生成后面

分块上传仍在读取前预留最大请求体预算。以前即使只读到几十字节，也会在排队期间持续占用该预算。现在确认上传结束后，保留 `cap(body) + len(body) + 8192` 字节：包括现有底层缓冲区、潜在请求体改写及原有余量，只退还多余预留。

4 MiB 请求体上限时，原预留为每请求 8,396,802 B；该回归测试的小请求实际保留约 12 KiB。16 MiB 总预算、所有账号槽位已占用的测试中，8 个小型分块请求可以排队，然后全部完成，最终预留归零。原公式在这项预算下只能容纳一个这样的持续预留。上传阶段的并发仍受最大预算保护；这不是总 RSS 上限或所有适配器内存的完整记账。

## 其他场景的决定

| 场景 | 处理 |
|---|---|
| 空闲短请求 | 保留现有无等待快速路径；本轮未增加缓存锁或后台任务 |
| 多账号突发请求 | 沿用上一轮定向唤醒、通知合并和可运行请求 FIFO；已有 256 请求/8 账号回归测试 |
| 长文本与真实图片 | 减少检测分配，保留实际图片标记与纯文本的区别，覆盖转义键和值 |
| 大请求与未知长度上传 | 保留上传前预留、大小限制及缓冲容量上限；读完后按实际保留量缩减预算 |
| 慢客户端、细粒度 SSE | 保留读取→写入的背压、逐块刷新、写入超时和输出限制；没有用批量延迟换取吞吐 |
| 频繁管理更新 | 模型列表每次读取当前启用状态；状态查询仍需快照，未引入过期状态缓存 |
| 真实浏览器与上游限流 | 本轮无真实账号长时压测；仍保留账号隔离限制和冷却，不声称提高了上游服务容量 |

## 验证

全量 `go test ./...`、`go vet ./...` 通过。API/协议回归重复五次通过；Linux API/协议/调度 race 检测通过。请求检查 fuzz 完成 1,674,422 次执行无失败；最终预筛选微调后重跑协议与 API 测试、race 检测通过。

100 并发、30,000 请求、每数据块 1 ms 的模拟 HTTP 测试中，直连与网关均零错误。微基准用于证明对应局部开销降低；短时同进程模拟测试用于验证集成行为，不用于证明生产吞吐增长。
