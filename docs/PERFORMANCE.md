## 选路与解析

`go test ./internal/routing ./internal/protocol -run '^$' -bench . -benchmem`

| 测试 | 时间 | 分配 |
|---|---:|---:|
| 8 个候选目标选路 | 223.7 ns/op | 0 B，0 次 |
| 100 个候选目标选路 | 2.772 µs/op | 0 B，0 次 |
| 1,000 个候选目标选路 | 27.478 µs/op | 0 B，0 次 |
| 约 8 KiB JSON 元数据检查 | 7.023 µs/op | 96 B，4 次 |

选路结果仅包含内部候选扫描，不包含锁竞争、排队、网络、解析或模型推理。JSON 检查约 1,178 MB/s，不代表完整 HTTP 请求吞吐。

## 100 并发流

`go run ./cmd/cot-bench -concurrency 100 -requests 1000`

模拟上游每次发送 4 个数据块，每块前等待 10 ms。客户端、网关和模拟上游同进程运行；先测直连，再测网关。TTFT 定义为第一个非空 SSE data 行，不包含浏览器或真实模型。

| 路径 | 成功/请求 | 请求/秒 | TTFT p50 | p95 | p99 |
|---|---:|---:|---:|---:|---:|
| 直连模拟服务 | 1000/1000 | 2240 | 10.999 ms | 17.874 ms | 19.871 ms |
| 经网关 | 1000/1000 | 2159 | 11.297 ms | 20.999 ms | 31.999 ms |

中位数差值为 0.298 ms；两个独立运行的百分位差不能解释为每个请求的精确开销。

## 未通过的高并发实验

1,000 并发、3,000 请求的冷连接突发实验未通过：直连和网关路径都出现大量 Windows `connectex: ... actively refused`，一次重复实验分别失败 2,688 和 2,716 次。失败发生在连接建立阶段，两条路径都受影响；当前证据不足以把问题归因于网关，亦不能宣称已支持 1,000 个同时活跃流。需要独立负载机、连接预热及 OS 队列诊断后再做容量验收。

尚未完成独立进程 RSS/CPU、长时间稳定性、真实网页 TTFT 和慢客户端持续压测。产品方案中的相关数字仍是待验收目标。

## 第二轮优化：调度与连接复用

同一 Windows/Go 环境，基准各运行 3 次，下表取中位数。

| 场景 | 修改前 | 修改后 | 范围 |
|---|---:|---:|---|
| 8 候选空闲选路 | 221.2 ns | 43.77 ns | 第一个可运行候选得分为 0 |
| 100 候选空闲选路 | 2715 ns | 40.39 ns | 同上，可提前结束 |
| 1000 候选空闲选路 | 25583 ns | 41.18 ns | 同上，不代表所有选路恒定时间 |
| 无排队获取/释放 | 393.7 ns，288 B，2 次分配 | 262.4 ns，176 B，1 次分配 | 8 来源；减少无接收者的通知通道分配 |
| 两轮 16 并发 HTTP 请求 | 28 条 TCP 连接 | 16 条 TCP 连接 | 第二轮完整复用；回归测试重复 5 次通过 |

1000 候选全部具有正延迟得分时仍完整扫描，本轮中位数 37.091 µs、0 分配；没有该场景修改前的同条件数据，不能宣称改善。零分提前结束保持原有旋转顺序，等待者唤醒、容量、共享额度、忙碌来源跳过和延迟选择均有测试覆盖。通用 HTTP 适配器空闲连接池按来源并发配置保留 4–256 条连接，仍受 60 秒空闲超时限制；空闲连接和内存保留量会相应增加。

同条件端到端复测：100 并发、3000 请求、每块 1 ms 延迟。前后均零错误；网关 RPS 18689→19135，TTFT p50 1.579→1.465 ms、p95 3.765→2.686 ms。总测试不足 1 秒且为同进程实验，这些数字只是单次观察，不作为稳定吞吐提升或生产容量结论。

验证：Windows `go test ./...`、`go vet ./...`；Linux `go test -race ./internal/routing ./internal/upstream ./internal/api` 全部通过。
