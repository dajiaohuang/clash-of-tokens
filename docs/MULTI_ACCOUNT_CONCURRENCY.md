# 多账号与 Agent 突发并发

2026-09-09，本轮优化针对大量请求排队时的调度开销。

## 已实现

原调度器每释放一个槽位就关闭共享通知通道，唤醒全部等待请求；请求再次争抢全局锁、扫描候选及前序等待者，并重新分配计时器。在多个账号收到突发请求时，这些工作多数无法获得槽位。

现在每个等待请求有独立通知通道，只唤醒最早可运行的请求；它离队后继续通知下一位，直到可用账号槽位填满。重复通知合并，计时器在等待期间复用。仍保留每 250 ms 的冷却恢复检查，因此极端队列规模下仍可能出现周期性扫描；没有声称完全消除队列成本。

保留全局并发限制、单 source 并发、共享 quota_domain 限制，以及当前可运行请求之间的 FIFO。一个繁忙账号的请求不会挡住后面能使用其他账号的请求。取消、停用、认证阻断和队列上限仍按原语义处理。

## 实测

Windows amd64、i9-14900KF、Go 1.27.1，每项三次取中位数。

| 基准：8 个账号被占满，再排队 128 请求后释放 | 修改前 | 修改后 |
|---|---:|---:|
| 每批完成时间 | 6.921 ms | 0.557 ms |
| 每批分配字节 | 1,174,581 B | 89,016 B |
| 每批分配次数 | 14,116 | 1,037 |

该调度微基准无真实网络及模型推理，约 12.4 倍改进只适用于这项突发调度测试。无排队 Acquire/Release 复测中位数 243.3 ns、176 B、1 次分配。

复现：`go test ./internal/routing -run '^$' -bench BenchmarkMultiAccountBurst -benchmem -benchtime=500ms -count=3`。

验证包括：256 请求/8 账号连续填满并排空、每账号最多一个活动请求、绕过繁忙账号、取消队首、停用后排空不可用请求、定向通知合并、FIFO 与无其他事件时冷却到期恢复。全量 Go 测试、vet、Linux routing/API race 检测通过；100 并发/30,000 请求的模拟 HTTP 端到端测试零错误。

## 多账号配置方式

HTTP 类 provider 的每个独立账号配置一个 source：相同 `provider`/`adapter`，不同 `id`，分别绑定各自的 `key_env`（需要时还有 `account_id_env`）。source 客户端独立且复用；请求相同模型 ID 或包含这些 sources 的 group 时可以跨账号调度。

- `source.max_inflight`：该账号允许同时运行的请求数，按实际账号能力设置。
- `quota_domain`：独立额度账号使用不同域；同账号的别名或共享组织额度必须复用相同域，防止重复计算容量。
- `quota_max_inflight`：该额度域的总并发上限，同域配置必须一致。
- `runtime.max_inflight`：整个网关的总并发上限；它可能先于账号总容量成为瓶颈。
- `runtime.max_queued`、`queue_timeout_ms`：控制超出活动容量后最多等待多少请求、等待多久。增大队列不会增加上游处理能力。
- group 使用 `auto` 可结合负载和延迟选路；`fallback` 优先填前面的 source；`select` 固定首个 source，不用于多账号分摊。

有状态对话仍需显式绑定 `source/model`，不能为提高并发而把后续轮次随机派给其他账号。浏览器类来源目前共用全局 browser 配置，复制 source 不会生成独立登录环境；本轮没有实现浏览器账号池。需要先隔离浏览器身份与会话存储，再启用该类多账号并发。

没有改动现有生产账号额度或自动提高并发配置；运行容量还受入口内存预算、上游限流及实际请求时长影响。
